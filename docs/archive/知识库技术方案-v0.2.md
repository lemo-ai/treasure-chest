# 袖里乾坤 · 知识库技术方案

> 版本：v0.2  
> 日期：2026-07-31  
> 原则：本机、无账号；**完整 RAG 能力一次设计到位**（非「先简陋再补」）  
> 对标：NotebookLM 类本地实现、RAGdoll / KnowNote / vstash 等 local-first 架构

---

## 0. 核心结论：切片进 SQLite —— 合适，而且是业界主流

### 0.1 直接回答

**合适。** 对本机桌面知识库，把 **chunk 文本 + 元数据** 放在 SQLite，是 2024–2026 local-first RAG 的主流做法，不是凑合方案。

| 业界常见分层 | 存什么 | 典型选型 |
|--------------|--------|----------|
| Blob / Object | 原始文件 | 本地目录 / S3 |
| System of Record | 文档元数据、**切片正文**、标签、版本 | **SQLite** / Postgres |
| Lexical index | 关键词（BM25） | **SQLite FTS5** / ES |
| Vector index | embedding | **sqlite-vec**（嵌入式）/ LanceDB / pgvector / Qdrant |

桌面端代表路径：

- **vstash**（论文/实现）：单库 SQLite = `documents` + `chunks` + `fts_chunks` + `vec_chunks(sqlite-vec)`，混合检索用 RRF  
- **RAGdoll / Psyche / KnowNote**：同样是 **SQLite 存 chunk + FTS5 + 向量（sqlite-vec）**  
- 服务端多租户才会上 Postgres+pgvector、或独立 Qdrant/Milvus——**那是规模与并发问题，不是「切片不该进 SQL」**

### 0.2 为什么切片适合 SQLite（而不是只丢向量库）

1. **Chunk 首先是文本记录**：要预览、引用高亮、按文档删除级联、按 symbol/标签过滤——关系库更合适  
2. **和 FTS 同库**：一次事务写入「切片 + 全文索引」，备份/迁移简单（外加 blobs 目录）  
3. **个人知识库量级**：通常是千～十万级 chunk；sqlite-vec 精确 KNN 完全可接受  
4. **向量库单独存正文**反而不香：Chroma/Lance 更擅长向量与 ANN；正文+强过滤仍常回落到 SQL 或双写

### 0.3 什么时候不该「只」靠 SQLite 向量

| 情况 | 做法 |
|------|------|
| 单机 chunk ≫ 50 万且要亚秒 ANN | 增加 **LanceDB** 作向量引擎，SQLite 仍作 SoR |
| 多机/多用户服务 | Postgres + pgvector 或 Qdrant——**不在本产品范围** |

**袖里乾坤定案**：  
**SQLite = 文档/切片/FTS 的权威存储；向量用 sqlite-vec 同库**；原文件磁盘 blobs。完整功能按混合检索设计，不把向量当「以后再说」。

## 1. 完整能力范围（产品 = 技术一次对齐）

| 能力 | 要求 |
|------|------|
| 多知识库 Collection | 创建/重命名/颜色/默认绑定 Agent |
| 用户上传 | md / txt / pdf / docx / html / csv；拖拽批量；hash 去重 |
| 系统入库 | 报告、资讯、运势、对话记忆 |
| 解析与切分 | 结构感知切分 + 重叠窗口；可重建索引 |
| **混合检索** | FTS5（BM25）+ 向量（语义）+ **RRF 融合** |
| 多样性 | 同文档限流 + **MMR**（避免一篇霸榜） |
| 可选重排 | 本地轻量 Cross-Encoder（设置开关） |
| Embedding | **双通道**：用户 Embedding API **与** 本地 ONNX 模型 |
| 引用 | 每条答案可溯源到 document/chunk；UI 强制展示 |
| 增量 | content_hash；未变跳过；变更则删旧 chunk 重切重嵌 |
| 运维 | 进度、失败重试、容量统计、整库重建、备份纳入导出包 |

不做：云账号同步、多租户 Hub、服务端 Qdrant 集群。

## 2. 总体架构（业界标准 RAG 管线）

```
┌────────────────── UI / Agent ──────────────────┐
│ 上传 · 收藏 · @知识库 · cite 胶囊 · 再分析增强   │
└─────────────────────┬──────────────────────────┘
                      │ IPC
┌─────────────────────▼──────────────────────────┐
│              Knowledge Runtime                  │
│  Ingest → Parse → Chunk → Segment → Embed       │
│  Index(FTS + Vec) → Retrieve(Hybrid+RRF+MMR)    │
│  [Optional Rerank] → ContextPack → Cite         │
└───────┬─────────────────────────────┬──────────┘
        │                             │
        ▼                             ▼
 userData/knowledge/blobs/     SQLite (WAL)
   原始文件不可变               documents / chunks
   (+ text cache 可选)         FTS5 + sqlite-vec
```

这与业界「Ingest → Chunk → Embed → Index → Hybrid Retrieve → Augment」同一套，只是全部跑在 Electron 主进程、数据不出本机。

## 3. 存储设计（完整版）

### 3.1 双介质

| 介质 | 路径/库 | 内容 |
|------|---------|------|
| 文件系统 | `userData/knowledge/blobs/{docId}/...` | 上传原件（权威字节） |
| 文件系统 | `userData/knowledge/derived/{docId}.txt` | 抽取纯文本缓存（加速重切分） |
| SQLite | 主库或 `knowledge.db`（建议 **独立 knowledge.db**，避免行情库膨胀；备份时打成一套） | 元数据、切片、FTS、向量 |

> 独立 `knowledge.db` 是工程偏好：业务行情库与知识库生命周期不同；逻辑上仍「本机 SQLite 存切片」。

### 3.2 Schema（完整）

```sql
PRAGMA journal_mode=WAL;

CREATE TABLE kb_collections (
  id TEXT PRIMARY KEY,
  name TEXT NOT NULL,
  description TEXT,
  color TEXT,
  agent_bindings_json TEXT,     -- 默认绑哪些 agent
  created_at TEXT NOT NULL,
  updated_at TEXT NOT NULL
);

CREATE TABLE kb_documents (
  id TEXT PRIMARY KEY,
  collection_id TEXT NOT NULL REFERENCES kb_collections(id),
  kind TEXT NOT NULL,           -- upload|stocks.report|stocks.news|fortune.daily|note|memory
  title TEXT NOT NULL,
  source_path TEXT,             -- blobs 相对路径
  mime TEXT,
  byte_size INTEGER,
  content_hash TEXT NOT NULL,   -- sha256(原件或规范化正文)
  parser TEXT,                  -- md|pdf|docx|html|structured
  status TEXT NOT NULL,         -- pending|parsing|chunking|embedding|ready|error
  error_message TEXT,
  version INTEGER NOT NULL DEFAULT 1,
  market TEXT,
  symbol TEXT,
  tags_json TEXT,
  meta_json TEXT,
  created_at TEXT NOT NULL,
  updated_at TEXT NOT NULL,
  indexed_at TEXT
);

CREATE TABLE kb_chunks (
  id TEXT PRIMARY KEY,
  document_id TEXT NOT NULL REFERENCES kb_documents(id) ON DELETE CASCADE,
  ordinal INTEGER NOT NULL,
  heading_path TEXT,
  content TEXT NOT NULL,        -- 展示与引用的原文切片
  content_seg TEXT NOT NULL,    -- 分词后（空格分隔）供 FTS
  token_est INTEGER,
  start_char INTEGER,
  end_char INTEGER,
  content_hash TEXT NOT NULL,   -- 单片 hash，便于增量
  meta_json TEXT,
  UNIQUE(document_id, ordinal)
);

CREATE VIRTUAL TABLE kb_chunks_fts USING fts5(
  chunk_id UNINDEXED,
  document_id UNINDEXED,
  collection_id UNINDEXED,
  title,
  body,
  tokenize = 'unicode61'
);

-- sqlite-vec：维度随模型配置（写入时校验一致）
-- 示例 dims=1536 或 768；用配置表记录当前 embedding_model + dims
CREATE VIRTUAL TABLE kb_chunk_vec USING vec0(
  chunk_id TEXT PRIMARY KEY,
  embedding float[768]
);

CREATE TABLE kb_embed_meta (
  chunk_id TEXT PRIMARY KEY REFERENCES kb_chunks(id) ON DELETE CASCADE,
  model TEXT NOT NULL,
  dims INTEGER NOT NULL,
  created_at TEXT NOT NULL
);

CREATE TABLE kb_jobs (
  id TEXT PRIMARY KEY,
  document_id TEXT,
  type TEXT NOT NULL,           -- ingest|reindex|embed_backfill
  state TEXT NOT NULL,
  progress REAL,
  message TEXT,
  created_at TEXT NOT NULL,
  updated_at TEXT NOT NULL
);
```

**要点**：切片正文在 `kb_chunks.content`；检索正文明文可查；向量只存数值，不替代正文。这是业界 SoR 写法。

### 3.3 与 LanceDB / Chroma 的对比（为何不默认换掉 SQLite 切片）

| 方案 | 切片正文 | 向量 | 适合 |
|------|----------|------|------|
| **SQLite + FTS5 + sqlite-vec**（采用） | SQL 表 | 同库 | 桌面、备份简单、过滤强 |
| LanceDB | 可作表列 | ANN 强 | 极大语料 / 要 version travel |
| Chroma | collection 文档 | 内存友好 | Python 原型多；Electron 非首选 |
| 独立 Qdrant | 常双写 | 服务级 | 有后端团队时 |

定案不排除日后 **向量热数据迁 LanceDB**，但 **chunk 文本权威仍在 SQLite**。

## 4. 解析与切分（完整策略）

### 4.1 解析组件

| 格式 | 组件 |
|------|------|
| md / txt | 原生 fs + 编码探测 |
| pdf | `unpdf` / `pdf-parse`（文本层）；扫描件标记 `needs_ocr` |
| docx | `mammoth` |
| html | 去标签转文本 / 转 md |
| csv | 转 Markdown 表或按行块 |
| 系统 JSON 报告 | 结构化字段映射为章节 |

### 4.2 切分（结构感知，非「固定字数一刀切」）

业界完整做法是 **层级切分 + token 窗口 + overlap**，不是 ML 语义切边界（语义切分贵且不稳，多数生产仍以结构+窗口为主）。

| 源 | 策略 |
|----|------|
| Markdown | AT1..AT3 为树；叶节点过长再按段落；再滑窗 |
| 长纯文本 / PDF | 段落合并到 `targetTokens`；`overlapTokens≈10–15%` |
| 代码（若以后支持） | 按语言 AST/正则块 |
| 资讯 | 1 条 = 1 chunk |
| 荐股报告 | 按标的 ×（摘要/理由/风险/资讯） |

默认参数（可设置）：

```
targetTokens: 512
maxTokens: 1024
overlapTokens: 64
minTokens: 64
```

实现：自研 `Chunker`（可测）；**不绑 LangChain**，逻辑等价于业界 chunk pipeline。

## 5. 索引与「算法」——完整检索栈

### 5.1 必须具备的算法/步骤

| 步骤 | 算法/技术 | 作用 |
|------|-----------|------|
| 中文分词 | jieba 等 | FTS 可用性 |
| 词法检索 | FTS5 **BM25** | 精确词、代码、标题 |
| 向量化 | Embedding 模型 | 同义/语义 |
| 向量检索 | sqlite-vec KNN（cosine/L2） | 语义召回 |
| 融合 | **RRF**（Reciprocal Rank Fusion） | 业界混合检索默认答案 |
| 去冗余 | **MMR** 或同文档配额 | 结果多样性 |
| 可选 | Cross-Encoder rerank | 精排 TopN |
| 打包 | 预算裁剪 + 引用编号 | 塞进 Context Window |

**RRF（标准式）**

\[
\mathrm{score}(c)=\sum_{r\in\{\mathrm{fts},\mathrm{vec}\}}\frac{w_r}{k+\mathrm{rank}_r(c)}
\quad(k=60)
\]

默认 \(w_{vec}=0.6, w_{fts}=0.4\)（可调；专名查询可自动提高 FTS 权重）。

### 5.2 Embedding 双通道（完整产品应同时支持）

| 通道 | 实现 | 何时用 |
|------|------|--------|
| **API** | OpenAI 兼容 `/embeddings`（复用用户已配的 Key/BaseURL） | 默认：质量稳、无本地大模型 |
| **本地** | ONNX Runtime + `bge-small-zh` / 多语 MiniLM 等；或用户本机 Ollama | 全离线、隐私优先 |

规则：

- 库级记录 `embedding_model` + `dims`；**换模型 = 全库向量回填任务**  
- 切片变更只重嵌该文档  
- 设置中明示当前通道与磁盘占用  

### 5.3 完整 Retrieve 管道

```
Query
  ├─ 分词
  ├─ FTS5 TopN1（含 collection/symbol/kind 过滤）
  ├─ Embed(query) → vec KNN TopN2（同过滤）
  ├─ RRF 融合
  ├─ 同 document 配额 / MMR
  ├─ [可选] Rerank TopM → TopK
  └─ ContextPack（token 预算）+ Cite[] → Agent
```

这就是业界「Hybrid RAG」完整形态；袖里乾坤按此实现，而不是只做关键字搜索。

## 6. 组件选型（完整栈）

| 职责 | 选型 | 说明 |
|------|------|------|
| 元数据 + **切片正文** | **better-sqlite3** | 业界桌面 SoR |
| 词法索引 | **FTS5** | BM25 |
| 向量索引 | **sqlite-vec** | 与 chunk 同库；个人规模足够 |
| 原件 | 磁盘 blobs | 不进 SQL BLOB |
| 分词 | `@node-rs/jieba`（验证 Electron） | 失败有 trigram 兜底但默认必须分词 |
| PDF / DOCX | unpdf、mammoth | |
| Embedding API | 现有 Provider 配置扩展 | |
| Embedding 本地 | onnxruntime-node + 小模型 或 Ollama | 设置可选 |
| 融合 / MMR | 自研（公式固定） | |
| Rerank（可选） | flashrank 类 ONNX 或 API rerank | 设置默认关，免拖垮 CPU |
| 任务队列 | 主进程持久化 `kb_jobs` | 可恢复 |

扩展预案：向量量爆炸时加 **LanceDB** 作 vec 后端，**不迁走 chunk 正文**。

## 9. 交付节奏（按子系统，不是砍功能）

完整功能分 **可并行子系统**，每一项都是完整设计的一部分，而不是「简陋版」：

| 子系统 | 内容 |
|--------|------|
| S1 存储与模型 | knowledge.db schema、blobs、Collection CRUD |
| S2 解析切分 | 全格式解析 + Chunker + 任务队列 |
| S3 词法索引 | 分词 + FTS5 + 过滤 |
| S4 向量索引 | Embedding 双通道 + sqlite-vec + 回填 |
| S5 混合检索 | RRF + MMR + ContextPack + Cite |
| S6 产品接通 | 上传 UI、系统入库、Agent/@、设置、备份 |
| S7 增强 | Rerank、监视文件夹、OCR（扫描 PDF） |

上线门槛建议：**S1–S6 齐备** 再标「知识库完整」；S7 为增强项但不改变架构。

## 10. 风险

| 风险 | 对策 |
|------|------|
| sqlite-vec 与 Electron/better-sqlite3 加载 | 启动探测；官方预编译；CI 三平台验证 |
| 换 embedding 模型 dims 变化 | 版本化 model id；一键回填；旧向量表迁移 |
| 中文 FTS | 强制分词；可加同义词（600519↔茅台） |
| 本地模型包体 | 默认 API 通道；本地模型按需下载 |
| DB 变大 | 独立 knowledge.db；blobs 外置；备份可选不含 blobs |

---

## 11. 一句话

> **切片存 SQLite 是业界 local-first RAG 的标准做法**；完整产品 = 同库 FTS5 + sqlite-vec + 混合 RRF/MMR + Embedding 双通道 + 磁盘原件，而不是「只做关键字 MVP」。  
> 只有做到超大规模 ANN 或服务化时，才把**向量引擎**换成 LanceDB/Qdrant，**切片正文仍应留在关系库作权威数据。**
