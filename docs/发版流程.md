# 发版流程

> 以后重新打 tag、发 GitHub Release，按本文操作即可。  
> 安装包由 GitHub Actions 云端打包上传，**不要**再本机慢传 DMG。

仓库：https://github.com/lemo-ai/treasure-chest  
工作流：`.github/workflows/release.yml`  
远程约定：`origin` = Codeup，`github` = GitHub（两边都推）。

---

## 0. 发版前检查

- [ ] 功能已在本机验证（`npm run typecheck` / 必要手动测）
- [ ] 工作区干净，或即将一并提交的改动已整理好
- [ ] 决定版本号：遵循语义化，如 `0.4.0` → `0.4.1` / `0.5.0`
- [ ] 本机已能 `git push github`（个人号对 `lemo-ai/treasure-chest` 有写权限）
- [ ] 本机已 `gh auth login`（仅在要用 `gh` 看 Actions / 手搓 Release 时需要）

---

## 1. 改版本与更新日志

### 1.1 `package.json`

把 `"version"` 改成新版本，例如 `"0.5.0"`（**不要**带 `v` 前缀）。

### 1.2 `config/changelog.json`

在 `releases` 数组**最前面**新增一条（应用内「版本变更」和 Actions Release 说明都读这里）：

```json
{
  "version": "0.5.0",
  "date": "2026-09-20",
  "title": {
    "zh-CN": "一句话中文标题",
    "en-US": "One-line English title"
  },
  "items": {
    "zh-CN": [
      "变更点 1",
      "变更点 2"
    ],
    "en-US": [
      "Change 1",
      "Change 2"
    ]
  }
}
```

`version` 必须与 `package.json` 一致；中英文都要写。

## 2. 提交并推送到 GitHub（以及 Codeup）

在仓库根目录：

```bash
cd /path/to/treasure-chest

git status
git add -A   # 或只 add 本次相关文件
git commit -m "chore: release 0.5.0"

# 双远程都推（顺序随意）
git push origin master
git push github master
```

确认 GitHub 上 `master` 已是最新提交：  
https://github.com/lemo-ai/treasure-chest/commits/master

---

## 3. 打 tag 并推送（触发自动打包）

标签格式必须是 **`v` + 版本号**，且与 `package.json` 一致，例如版本 `0.5.0` → tag `v0.5.0`。

### 3.1 新版本（推荐）

```bash
git tag -a v0.5.0 -m "v0.5.0"
git push github v0.5.0
git push origin v0.5.0   # Codeup 同步一份，可选但建议
```

推送 `v*` 到 GitHub 后，会自动跑 **Release** workflow：多平台打包并把产物挂到 Release Assets。

### 3.2 同一版本需要「重打 tag」再发一次

仅当：上次构建失败、或 tag 指错了提交、需要在**同一版本号**上重新发布。

```bash
# 1）如已有正式/草稿 Release，先删掉（保留或不保留 tag 按情况）
gh release delete v0.5.0 --repo lemo-ai/treasure-chest --yes

# 2）删远程 + 本地 tag
git push github :refs/tags/v0.5.0
git push origin :refs/tags/v0.5.0   # 若 Codeup 也有
git tag -d v0.5.0

# 3）在正确的 commit 上重建并推送（会再次触发 Actions）
git checkout master
git pull github master
git tag -a v0.5.0 -m "v0.5.0"
git push github v0.5.0
git push origin v0.5.0
```

注意：

- **不要**对已有 tag 用 `git push --force` 乱指，除非明确要覆盖；上面「先删再重建」更清晰  
- 删 Release 时**不要**加 `--cleanup-tag`，除非你打算马上重建 tag；误加会把远程 tag 一起删掉  
- 用户若已下载旧包，同版本重发可能造成混淆；能升小版本（`0.5.1`）更稳妥  

### 3.3 不重打 tag，只对已有 tag 再跑一遍构建

Actions → **Release** → **Run workflow** → 填入已有 tag（如 `v0.5.0`）→ Run。  
适用于：workflow 修好了、想对旧 tag 补传产物。

## 4. 盯构建与产物

1. Actions：https://github.com/lemo-ai/treasure-chest/actions/workflows/release.yml  
2. 通过后打开 Release：https://github.com/lemo-ai/treasure-chest/releases  
3. Assets 里应有例如（**安装包文件名必须是 ASCII**，避免 GitHub 剥离中文导致 `-0.6.0.dmg`）：
   - `treasure-chest-x.y.z-arm64.dmg` / `treasure-chest-x.y.z-x64.dmg`（mac；磁盘里的 App 仍叫「袖里乾坤」）
   - `treasure-chest-setup-x.y.z.exe`（Windows）
   - Linux `.AppImage` / `.deb`
4. `.blockmap` 是增量更新索引，**不是**安装包；普通用户下 `.dmg` / `.exe` 即可  

未配置 Apple 证书时，macOS 可能提示「无法验证开发者」或「已损坏」——多为未签名 + 隔离属性，**不一定是真损坏**（见 §6）。应用内显示名仍是「袖里乾坤」。

## 4.1 macOS 签名与公证（可选）

**无私钥时（默认）**：CI 不注入 `CSC_LINK`，`CSC_IDENTITY_AUTO_DISCOVERY` 为 `false`，打出未签名 DMG；`scripts/notarize.js` 会跳过公证。应用内「检查更新」仍可用，但自动安装在未签名包上可能失败，可引导用户到 Releases 手动下载。

**有 Developer ID 时**：在 GitHub 仓库 Settings → Secrets 配置：

| Secret | 说明 |
|--------|------|
| `CSC_LINK` | Developer ID Application 证书 `.p12` 的 base64（或 CI 可读路径） |
| `CSC_KEY_PASSWORD` | p12 密码 |
| `APPLE_ID` | Apple ID 邮箱 |
| `APPLE_APP_SPECIFIC_PASSWORD` | [App 专用密码](https://appleid.apple.com) |
| `APPLE_TEAM_ID` | 团队 ID |

配置后 Release workflow 会自动签名；`afterSign` → `scripts/notarize.js` 在三组 Apple 变量齐全时公证。`electron-builder.yml` 已开启 `hardenedRuntime` 与 `resources/entitlements.mac.plist`（含麦克风权限，供工作台语音输入）。

**本机未签名打包**：直接 `npm run dist`，不设上述环境变量即可。

签名包才能与 `electron-updater` 的自动安装顺滑配合。

### 排障（mac）

| 现象 | 处理 |
|------|------|
| `CSC_LINK not a file` | Secret 为空字符串被注入；workflow 已在空值时 `unset`，确认 Secret 未设成空格 |
| 公证超时 / 401 | 核对 App 专用密码与 Team ID；Apple ID 需有该证书权限 |
| Gatekeeper 仍拦 | 确认产物已公证且用户从 GitHub Releases 下载（勿改文件名破坏签名） |
| 提示「已损坏」无法打开 | 未签名包常见误报。终端执行：`xattr -cr /Applications/袖里乾坤.app` 后再开；或右键 → 打开 |
| 麦克风无权限 | 系统设置 → 隐私 → 麦克风；Info.plist 已含 `NSMicrophoneUsageDescription` |
| Assets 文件名变成 `-0.6.0.dmg` | 安装包名含中文被 GitHub 剥离。`artifactName` 须用 ASCII（`treasure-chest-…`），`productName` 仍可中文 |

## 4.2 Windows 代码签名（可选）

**无证书时（默认）**：打出未签名 NSIS `.exe`；应用内更新可能无法静默安装，UI 会引导打开发布页手动下载。

**有 Authenticode / EV 证书时**，配置其一：

| Secret | 说明 |
|--------|------|
| `WIN_CSC_LINK` | Windows 代码签名证书 `.p12` / `.pfx` 的 base64（优先） |
| `WIN_CSC_KEY_PASSWORD` | 对应密码 |
| 或复用 `CSC_LINK` / `CSC_KEY_PASSWORD` | 若与 Mac 共用同一套 secret 命名也可（workflow 会回退读取） |

有证书时 CI 将 `CSC_IDENTITY_AUTO_DISCOVERY=true`；否则明确跳过并打印日志，避免空路径误伤。

### 排障（Windows）

| 现象 | 处理 |
|------|------|
| SmartScreen 警告 | 未签名或新证书信誉不足；签名 + 时间戳后随下载量改善 |
| 自动更新失败 | 确认发行包已签名且 `latest.yml` 与 exe 同 Release |

## 6. 常见问题

**Q: 推了 tag 但没有跑 Release？**  
确认 tag 名是 `v0.5.0` 这种（以 `v` 开头）；确认推的是 `github` 远程；到 Actions 看是否被 concurrency 取消或权限失败。

**Q: prepare 报 changelog 对不上？**  
`config/changelog.json` 里必须有与 tag 去掉 `v` 后相同的 `version` 字段。

**Q: 某一端（如 Windows）失败？**  
看对应 job 日志；修代码或 workflow 后，用 §3.2 重打 tag，或 §3.3 手动 Run workflow。

**Q: 还要不要本机 `npm run dist`？**  
日常发版不需要。本机 dist 只用于自己验证安装包；正式对外以 Actions 产物为准。

**Q: Codeup 和 GitHub 不一致？**  
发版以 GitHub 为准；平时养成 `origin` + `github` 双推，避免只推一边。

**Q: 下载的安装包没有中文名 / 打开提示损坏？**  
安装包文件名故意用 ASCII（`treasure-chest-…`），应用内名称仍是「袖里乾坤」。未签名 macOS 包常被 Gatekeeper 误报「已损坏」，用 `xattr -cr /Applications/袖里乾坤.app` 清除隔离后再打开；有正式签名公证后可避免。

**Q: 未签名包「检查更新」后装不上？**  
预期行为：可检查与下载引导，自动安装依赖签名；请用 Releases 手动覆盖安装。
